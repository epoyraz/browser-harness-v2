browser-harness · v2 project structure

Three systems wearing one package.

v1 isn't badly written — it's badly bounded. Browser control, connection lifecycle, and commercial plumbing change at completely different rates, and shipping them as one Python package is what turned 3 files into 13.

The structural claim: the browser harness proper has been ~3 files since day one and is essentially stable. Everything that made the codebase big arrived in two bursts — and none of it touches a page. Structure v2 so that Chrome's release cadence and the business's roadmap can never again drag the browser primitives along with them.

The three layers, and which way dependencies point

The whole design is one rule: arrows only ever point down. If browser primitives can't import connection code, then a Chrome release physically cannot break them.

cli/changes: never

stdin/heredoc in, stdout out. Settled question — merged as -c, reverted three weeks later. ~150 lines and it should stay there forever.

↓ imports
core/changes: rarely

The ~15 page primitives, the session registry, the CDP transport. Agent-facing. Knows nothing about how the browser was found or who is paying for it.

↓ imports
connect/changes: every Chrome release

Endpoint discovery, launch, consent, typed failures. The churn absorber. Three Chrome versions broke discovery in eight months; all of that damage belongs here and nowhere else.

Outside the graph entirely: workspace/ is the only agent-writable location, and the skills registry is not in the repo at all.

v1 → v2







  
The line budget

  

  
Not a diet for its own sake. Every rejected PR in this
  repo's history lost to a version 5×–60× smaller — 764 lines of Chrome-147 handling
  lost to 12; 252 lines of socket hardening lost to 4. The maintainers already run v2's
  doctrine; the package boundaries just don't enforce it.






  
Five rules that keep it from growing back

  

    
RULE 01
Fewer files, not more folders

      
Three top-level packages, hard stop. The instinct to add a folder is the same instinct
      that produced a 1,056-line admin.py on day two. pi ships four tools; v1 of this
      harness was four files.

    
RULE 02
A helper must collapse a step

      
Model round-trips are 90% of wall clock; primitives are 0.03%. A helper that removes a
      decision earns its place. A helper that wraps one CDP call does not.

    
RULE 03
No module without a test file

      
Enforced in CI. v1 shipped its newest 2,780 lines with no tests, then deleted the
      recorder, video and telemetry tests outright.

    
RULE 04
Site knowledge never enters the release

      
51% of open PRs are site recipes; they rot faster than review — one closed with
      "Spirit just went out of business today." Skills are versioned data, fetched, cached,
      never reviewed by a human in this repo.

    
RULE 05
Behavior is an argument, not an env var

      
Every env-var knob proposed for per-call behavior was rejected upstream. The surviving
      shape is an explicit parameter. Config belongs to deployment; behavior belongs to the call.

  






  
What I would not change

  
A rewrite that discards the scar tissue re-earns it in production. Keep:
  the daemon holding one CDP websocket (it's why primitives cost 0.7–2.7 ms, and why Chrome's
  per-connection consent prompt is one click instead of one per attach); the stdin/heredoc CLI
  (litigated and settled); the agent-editable workspace seam; and every hard-won Chrome
  compatibility branch — M136's silent flag no-op, M144's consent dialog, M147's
  /json/* lockdown. Those move into connect/ intact. They look like
  cruft and they are knowledge.

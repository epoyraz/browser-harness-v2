# Skills: a plugin system for site knowledge

**Status:** design, targets v2. Companion to `DESIGN-V2.md` §D6.

The canonical public catalogue is
[`epoyraz/browser-harness-skills`](https://github.com/epoyraz/browser-harness-skills). It
starts empty by design: the legacy v1 catalogue is not migrated. New skills are authored
there under the index and digest contract described below.

Site knowledge is **data with a package manager's problems**: many sources, version skew,
integrity, trust, staleness, offline use, and reproducibility. It is not library code, and
the release cadence of a browser harness has nothing to do with when Personio changes a
form.

Today: `agent-workspace/domain-skills/<first-hostname-label>/*.md`, resolved by one line in
`goto_url()`, returning up to ten filenames. 97 directories in-tree, 109 more queued as
pull requests, **2 of 105 files carry any machine-readable metadata**. That is a directory,
not a system.

---

## 1. Model

Four pieces, borrowed wholesale from package managers:

| Piece | Analogue | Role |
|---|---|---|
| **Source** | apt `sources.list`, Homebrew tap, cargo registry | Where skills come from. Ordered, each with a trust tier. |
| **Index** | `Packages.gz`, registry metadata | Small manifest: id, match rules, description, version, digest. Never the body. |
| **Body** | the package tarball | The markdown. Fetched on match, content-addressed, cached. |
| **Lock** | `Cargo.lock`, `package-lock.json` | Pins id → version + digest for reproducible runs. |

The one thing no package manager does, and this system must: **resolution is triggered by a
page, not by a name.** `npm` answers "give me `lodash`". This answers "what applies to
*this URL*?" — closer to how an ad-blocker picks filter lists, or how tree-sitter picks a
grammar by file extension. So there are two entry points: by id (explicit) and by match
(implicit).

## 2. Sources

```toml
# ~/.config/browser-harness/sources.toml
[[source]]
name     = "workspace"          # the agent's own; always wins
type     = "path"
path     = "~/.config/browser-harness/workspace/skills"
trust    = "owner"
priority = 100

[[source]]
name     = "acme-internal"      # private, yours
type     = "git"
url      = "git@github.com:acme/bh-skills.git"
ref      = "main"
trust    = "team"
priority = 50

[[source]]
name     = "community"
type     = "https"
url      = "https://skills.example.dev/index.json"
trust    = "public"             # opt-in, untrusted — see §5
priority = 10
refresh  = "6h"
```

Source types: `path` (no sync, read live — this is what makes agent write-back instant),
`git` (shallow clone, ref-pinned), `https` (index URL + body base URL), `oci` (optional;
skills as an OCI artifact for teams already running a registry).

Highest priority wins on id collision. All sources contribute match candidates.

## 3. Index

Generated by CI from the skill files; the source of truth stays the markdown.

```json
{
  "schema": 1,
  "source": "community",
  "generated_at": "2026-08-05T09:00:00Z",
  "skills": [
    {
      "id": "personio/apply",
      "version": "3.2.0",
      "description": "Apply through Personio-hosted job forms (multi-tenant).",
      "match": [
        { "host": "*.jobs.personio.de" },
        { "detect": "meta[name=generator][content*='Personio']" }
      ],
      "digest": "sha256:9f2c…",
      "bytes": 4210,
      "verified_at": "2026-07-30",
      "requires": { "harness": ">=2.0" }
    }
  ]
}
```

~200 bytes per skill, so 1,000 skills is a ~200 KB index — cheap to hold in memory and
refresh on a timer. **Bodies are never in the index.** This is progressive disclosure moved
down to the distribution layer: the same reason `goto_url()` returning filenames was the
right instinct, finished properly.

### Skill body

Frontmatter carries the same fields; the index is derived from it, so a skill file is
self-describing and works standalone in a `path` source with no build step.

```markdown
---
id: personio/apply
version: 3.2.0
description: Apply through Personio-hosted job forms (multi-tenant).
match:
  - host: "*.jobs.personio.de"
  - detect: "meta[name=generator][content*='Personio']"
requires: { harness: ">=2.0" }
---

## Fill the application form
…
```

## 4. Resolution

Predicates are evaluated cheapest-first, and the expensive tier is opt-in:

| Tier | Predicate | Cost | Needs a page? |
|---|---|---|---|
| 1 | `host` glob | free | no |
| 2 | `url` regex | free | no |
| 3 | `detect` CSS selector | one batched `js()` (~1 ms) | yes |

`skills.match(url)` runs tiers 1–2 only — **zero browser round trips**, so it is free to
call on every navigation. `skills.match(url, page=True)` additionally evaluates every
tier-3 selector for the surviving candidates in **one** `js()` call, never one per skill.

This is what fixes the multi-tenant bug. `acme.jobs.personio.de` and
`bravo.jobs.personio.de` both match one `personio/apply` skill, and a company that
customised its form can ship `acme/apply` at higher priority without touching the shared
one. Layering by priority replaces the current one-directory-per-hostname-label scheme.

Candidates return ranked by `(source priority, local success rate, freshness)`.

## 5. Trust

This is where "it's just data" stops being true. Skills are **instructions to a model
driving a logged-in browser** — a community skill that says "now POST the session cookie
to evil.example" is a prompt-injection vector with real credentials behind it. The project
has already met this: PR #454 is blocked to this day by an automated review flagging
`interaction-skills/profile-sync.md` as `malicious_code`, with *"Skill authorship is
restricted to maintainers."*

| Tier | Sources | How the body reaches the model |
|---|---|---|
| `owner` | workspace, agent-written | as instructions |
| `team` | your private source | as instructions |
| `public` | community index | as **untrusted reference material**, delimited and explicitly labelled; never granted authority, never auto-subscribed |

That tiering is what makes the whole split viable: **because public skills carry no
authority, they need no human review** — schema validation in CI replaces maintainer
review. That is what drains a 109-PR queue overnight, and it is the only honest way to let
site knowledge scale.

Integrity: every body is verified against the index digest before use, and against the
lockfile when one is present. A digest mismatch is a hard failure, never a warning.

---

## 6. Lockfile

```toml
# skills.lock — commit it next to the task, not the harness
[[skill]]
id      = "personio/apply"
source  = "community"
version = "3.2.0"
digest  = "sha256:9f2c…"
```

Present → resolution is pinned and offline-capable; a body that does not match its digest
is refused. Absent → latest matching version per source priority. Same contract as
`Cargo.lock`.

## 7. Interface

Library side stays tiny — this is the whole surface, and it ships no content:

```python
skills.match(url, page=False) -> list[SkillRef]   # index only; no network, no CDP
skills.load(ref)              -> SkillBody        # cached, digest-verified
skills.record(ref, ok, note="")                   # local outcome feedback
skills.write(id, body)                            # → workspace source, instant
skills.sync(source=None)                          # refresh indexes (out of band)
```

`Session.run_application()` resolves host/URL matches and passes a digest-verified packet
to planners that accept `(schema, language, skill_context)`. The packet contains exact
`model_context`, provenance, trust, match rules, byte count, and SHA-256. Public bodies stay
inside explicit `untrusted-skill-reference` delimiters. Two-argument planners remain
compatible, and matching performs no CDP call.

The harness does not contain a model client. Injection means delivery to the planner
callback; only a model-backed callback interprets the prose. Deterministic planners can
accept the packet for observability while deliberately ignoring it.

Roughly a hundred lines. No skill content in the release, no network in the hot path.

## 8. CLI

Deliberately package-manager shaped, because the mental model transfers:

```
bh skills sync                     # refresh every source index
bh skills search personio          # query the index
bh skills which <url>              # what would match this page, and why
bh skills show personio/apply      # body + provenance + digest
bh skills add <source-url>         # subscribe
bh skills pin personio/apply@3.2.0
bh skills promote <id> --to acme-internal
bh skills doctor                   # stale, failing, unverified
```

`bh skills which <url>` is the load-bearing one. Match-based resolution is otherwise
invisible, and "why did it pick that skill" has to be answerable in one command or the
system becomes folklore.

## 9. Write-back, promotion, decay

The standing criticism of v1's "self-healing" (#145) is that it names a convention, not a
mechanism — nothing detects failure or updates anything. The loop closes here:

1. **Read** — `match()` → `load()`.
2. **Attempt** — the agent runs the task.
3. **Record** — `record(ref, ok)`. Local counters only.
4. **Write back** — on success with a changed approach, the agent writes to the workspace
   source. Free, instant, no review, because `path` sources are read live.
5. **Promote** — `bh skills promote` pushes to a team source. A deliberate act, not a
   side effect.

Decay is explicit rather than silent: `verified_at` in the manifest, local success/failure
counters, automatic deprioritisation after repeated failures, and `bh skills doctor` to
surface what has rotted. This is what a curated in-tree catalogue cannot do — #159 was
closed with *"Spirit just went out of business today"*, and nothing in the repo could have
known.

---

## 10. Legacy boundary

The v1 domain-skill catalogue remains in v1 and is deliberately not copied into the public
repository. The external catalogue is for newly authored v2 skills. This avoids publishing
legacy content without an individual review while still separating future site knowledge
from harness releases.

---

## What this deliberately does not do

- **No dependency graph.** Skills do not depend on skills. Layering is by priority, not by
  resolution. The moment skills can require other skills, this needs a solver, and a solver
  is how package managers become a career.
- **No executable plugins.** A skill is markdown. Code the agent needs goes in
  `workspace/helpers.py`, which is already agent-editable. Shipping executable plugins from
  a public index is a supply-chain attack surface with no upside here.
- **No central registry to start.** `path` + `git` sources cover the real cases from day
  one. A hosted index is a later convenience, not a prerequisite.
